# 프로젝트 상태

기준일: 2026-11-04

## 확정 사항

- 분석 저장소: `yongin-public-data-ai`. 수집 저장소: `yongin-public-data-collector`.
- 수집 워크플로 `YNGN01CollectWk1`과 질문 워크플로 `YNGN02AnalysisV1`을 기존 로컬 n8n에서 분리한다.
- 분석은 `analytics` 뷰만 읽으며, 미리 정의한 파라미터 SQL로 계산한다. LLM 연결은 아직 검증되지 않았다.
- 운영 DB에는 현재 `giheung_events` 1종이 적재되어 있다. 시설과 다른 구의 자료는 없다.

## 완료·검증 작업

- 기존 프로젝트의 Python 구조, `.venv`, 환경변수 검증, DB 연결 검사, 로깅, 비밀정보 제외 규칙과 private GitHub 저장소를 유지했다.
- 기존 원본 수집 공통 모듈과 수지구 생활체육 프로그램 HTML 원본 수집 기록을 유지했다. 이 HTML은 현재 운영 분석 대상이 아니다.
- 기존 `8090/ask → n8n → Python 분석 서비스 → Supabase` 경로로 대표 질문 3개를 실행했다.
- 직접 읽기 전용 SQL과 서비스 응답이 전체 781건, 2024년 105건, 2024년 월별 합계 105건으로 일치했다.
- 시설 질문은 `unsupported`, 2030년 질문은 `empty`, 연도 없는 5월 질문은 `clarification` 응답을 확인했다.
- Streamlit 화면을 기존 `/ask` 서비스에 연결하고 답변, 표, 월별 막대그래프, 출처, 날짜, 계산 기준, 해석 한계를 표시한다.
- 수집 스키마·마이그레이션·데이터셋 등록·수집 워크플로는 수정하지 않았다.
- 분석 저장소 테스트 11개와 Python 문법 검사를 통과했다. Streamlit 화면에서 대표 질문 3개를 제출해 예외 없이 답변과 표가 표시됨을 확인했다.

## 미확인 사항

- 시설 API와 추가 2종 데이터의 실제 적재 및 분석.
- LLM 연결과 설명 정확도 평가. 현재 분석 서비스는 규칙 기반이다.
- 분석 서비스의 별도 읽기 전용 로그인 DSN. 현재는 관리자 DSN 접속 후 읽기 전용 트랜잭션과 `SET ROLE yongin_analysis_reader`를 적용한다.
- 운영 컨테이너를 중단하는 장애 시험은 수행하지 않았다. 별도 임시 환경에서 잘못된 DB 접속 주소를 주입해 분석 함수의 `error` 응답과 결과 행 0을 확인했다.

## 다음 작업

1. 수집 담당자가 계약에 따라 추가 데이터 2종을 검증·적재한 후 지원 질문을 확장한다.
2. 분석 서비스에 전용 읽기 전용 로그인 DSN을 적용해 관리자 DSN을 분석 런타임에서 제거한다.
3. LLM 키와 평가 질문이 준비되면 의도·조건 추출 및 설명에만 연결하고 수치 계산은 SQL로 유지한다.
