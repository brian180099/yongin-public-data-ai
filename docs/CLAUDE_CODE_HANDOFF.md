## 2. 사용자가 결정한 제품 범위

초기 `AGENTS.md`는 생활여가·문화·체육 MVP를 지시한다. 이후 사용자가 공공데이터포털에서 `용인`, `용인시`로 검색되는 CSV 중 **제공기관이 정확히 `경기도 용인시`인 자료 전체**를 로컬 PostgreSQL에 적재하도록 명시적으로 확장했다. 다른 제공기관 자료 67종은 제외한다. 현재 웹은 적재된 용인 관련 허용 자료 전체를 조회한다.

이 후속 지시가 현재 데이터 범위의 기준이다. 범위를 다른 기관으로 넓히거나 다시 3개 MVP로 축소하지 마라. 수집 원본을 수정하지 말고, 분석 통계를 수집 프로젝트에 추가하지 마라.

## 3. 현재 실행 구조

```text
사용자 브라우저 http://localhost:8501
  → Streamlit 웹
  → n8n POST /webhook/yongin-analysis-v1
  → yongin-question-agent:8091/v1/analyze
  → OpenAI Responses API: 질문을 구조화된 조회 계획으로만 변환
  → 서버가 데이터셋·컬럼·필터·연산·질문 원문 일치 여부 검증
  → yongin_analysis_login 읽기 전용 연결
  → analytics.dataset_sources / analytics.current_dataset_records
  → SQL 계산 결과와 출처를 한국어 응답으로 반환
```

실행 중인 컨테이너:

- `yongin-local-postgres`: 로컬 PostgreSQL, 호스트 `127.0.0.1:5435`
- `yongin-collector`: 수집 서비스, 호스트 `127.0.0.1:8088`
- `yongin-question-agent`: 분석 API, 호스트 `127.0.0.1:8091`
- `yongin-question-web`: Streamlit, 호스트 `127.0.0.1:8501`
- `n8n`, `n8n-runners`: 기존 n8n

n8n 워크플로 ID는 `YNGN02AnalysisV1`, Webhook은 `/webhook/yongin-analysis-v1`이다. n8n은 질문 전달과 실행 기록만 맡는다. 실제 분석·답변은 `yongin-question-agent` 한 경로에서 만든다. 수집 저장소의 이전 `yongin-analysis` 서비스를 다시 시작하지 마라. 서로 다른 답을 만드는 이중 경로가 생긴다.

## 5. 이미 구현된 기능

- DB에서 데이터셋 목록을 동적으로 읽는다. 데이터셋 ID와 행 수를 코드에 고정하지 않는다.
- 질문이 모호하면 최대 5개 후보를 반환하고 웹에서 버튼으로 선택해 원래 질문을 재실행한다.
- OpenAI는 SQL이나 최종 답변을 만들지 않고 JSON Schema 구조의 자료 선택·조회 계획만 만든다.
- 모델 계획의 데이터셋 ID, 연산, 컬럼, 필터 값, 질문 원문과의 일치 여부를 서버가 다시 검증한다.
- 모델이 질문에 없는 검색어·분류·날짜 조건을 추가하면 계획을 거절하고 안전한 규칙 경로를 사용한다.
- 지원 연산: 전체 건수, 전체 JSON 값의 부분 문자열 검색, 조건별 건수, 검증된 날짜 컬럼의 월별·연도별 집계, 검증된 지역·분류 컬럼의 그룹 비교, 제한된 원본 행 표시.
- 후속 질문은 `그중에서`, `월별로 다시`처럼 명시적인 표현이 있고 직전 데이터셋이 일치할 때만 검증된 문맥을 이어받는다.
- 결과에 데이터셋명, 제공기관, 공식 포털 URL, 데이터 기준일, 수집일, 적용 필터, 계산 방법을 포함한다.
- 등록 현황을 운영 중·예약 가능·현재 행사로 단정하지 않는다.
- 읽기 전용 트랜잭션, 별도 로그인, 역할 전환, SQL 제한 시간 5초를 사용한다.
- 원본 행은 최대 20건, 행당 4KB, 그룹 결과는 최대 50개다.
- 임의 SQL과 DB 쓰기 요청, 다른 도시 요청을 거절한다.
- OpenAI 키가 없거나 모델 계획이 실패하면 가능한 기본 질문만 규칙 기반으로 처리한다.
- 웹 UI는 사용자용으로 간결하게 정리했다. 제목, 예시 질문, 채팅 입력, 결과 건수·표·차트만 기본 노출한다. 기술 용어와 모델 상태는 숨기고, 출처와 조회 기준은 접힌 영역에서 제공한다.

검증 완료 상태:

- OpenAI 키를 사용한 실제 Responses API 구조화 출력 호출 성공
- 실제 n8n Webhook 경유 성공
- Streamlit 예시 질문·건수·출처 링크 표시 성공
- Streamlit 모호한 자료 후보 선택 후 재실행 성공
- 웹·API 상태 HTTP 200

OpenAI 구조화 출력은 공식 문서의 `text.format` + `json_schema` + `strict: true` 방식을 사용한다. 현재 기본 모델은 `gpt-4o-mini`이며 `OPENAI_MODEL` 환경 변수로 바꿀 수 있다.

## 7. 비밀과 데이터 보호

절대 출력하거나 Git에 포함하지 말 것:

- `.runtime/` 전체

분석 저장소의 사용자가 입력한 OpenAI 키는 Git 제외 `.env`에 있고, 실행 컨테이너에는 Git 제외 `.runtime/analysis-container.env`를 통해 전달된다. 키 값 자체를 확인용 출력, 테스트 출력, 로그, 예외 메시지에 노출하지 마라. 존재 여부만 Boolean으로 확인한다.

DB 역할:

- 수집·적재: `yongin_collector_login`
- 분석: `yongin_analysis_login`
- 분석 코드는 `session_user`가 읽기 전용 로그인인지 확인하고 `yongin_analysis_reader` 역할로 전환한다.

LLM이 만든 SQL을 실행하지 마라. SQL은 서버에 미리 정의된 파라미터화 쿼리만 사용한다. 모델 출력은 언제나 불신하고 실제 계약과 질문 원문으로 검증한다.

## 8. 원본·품질 불변 조건

- 원본 바이트, 수집일, 데이터 기준일, SHA-256을 보존한다.
- 원본 CSV를 수정하거나 임의 중복 제거하지 않는다.
- 동일 내용 중복 행은 내용 해시와 출현 순번을 조합해 별도 레코드로 유지한다.
- 이름 없는 헤더는 운영 payload에서만 `__unnamed_column_N`으로 이름을 붙인다.
- 완전히 빈 패딩 행은 품질 기록에 개수를 남기고 운영 레코드에서 제외한다.
- 잘못된 날짜 문자열은 유효 날짜로 보정하거나 추정하지 않는다.
- 스키마·건수·필수값 검증을 통과한 자료만 운영 레코드에 반영한다.
- 적재 실패 시 트랜잭션을 롤백하고 이전 정상 레코드를 유지한다.
- 기존 Supabase 원본·현재 레코드·변경 이력과 두 저장소의 Git 이력을 보존한다.
- force push를 사용하지 않는다.

## 10. 계속 개발해야 할 포인트

### 우선순위 P0: 정확성과 회귀 방지

1. **자료별 분석 가능 컬럼 계약을 명시적으로 관리**하라. 현재 `_columns()`가 질문 시 JSONB 전체 값의 형식과 고유값 수를 검사한다. 1천만 행 이상 DB에서 느리거나 5초 제한에 걸릴 수 있다. 수집 원본이나 수집 통계에 분석 로직을 넣지 말고, 분석 저장소 또는 별도 `analytics` 계약 테이블에 검증 결과를 버전·원본 SHA와 함께 캐시하는 방안을 설계하라.
2. **모델 계획 적대·오해 테스트를 확장**하라. 자료명을 검색어로 재사용, 따옴표 내부 단어를 분류로 추가, 연도 숫자를 월로 오인, 질문에 없는 지역 조건 추가, 다른 데이터셋 문맥 상속을 계속 회귀 테스트하라.
3. **대용량 자료 성능**을 측정하라. 단순 건수는 빠른 경로가 있지만 JSONB 부분 검색·컬럼 프로파일·그룹 집계는 느릴 수 있다. 실제 쿼리 계획을 읽기 전용으로 확인하고 필요한 분석 전용 인덱스나 사전 검증 메타데이터를 제안하라. 원본 스키마는 변경하지 마라.
4. 오류를 전체 건수로 바꾸지 마라. 지원하지 않는 조건과 시간 초과는 이유를 분명히 반환한다.

### 우선순위 P1: 사용자 경험

1. 현재의 간결한 UI 원칙을 유지하라. 기본 화면에 OpenAI, n8n, PostgreSQL, 구조화 계획 같은 구현 용어를 다시 노출하지 마라.
2. 316개 자료 목록을 한 표로만 보여 주지 말고 검색, 주제·기관 필터, 페이지 나누기 또는 관련 자료 추천을 추가하라.
3. 후보 자료 선택 시 사용자가 구분할 수 있도록 자료명 외에 제공기관·기준일·간단한 컬럼 설명을 표시하되 화면을 과도하게 복잡하게 만들지 마라.
4. 표 컬럼명을 사용자 친화적으로 표시하고 긴 원본 값, 빈 값, 날짜 표기를 정리하라. 원본 자체는 바꾸지 마라.
5. 모바일 폭, 키보드 탐색, 색 대비, 스크린 리더 레이블을 확인하라.
6. 응답 대기 중 취소·재시도와 친절한 오류 복구를 추가하라. 내부 서비스명과 스택 추적은 숨긴다.
7. 브라우저 새로고침 시 대화 문맥은 사라진다. 세션 보존이 필요하면 질문 원문과 개인 정보 저장 정책부터 정하고 최소한으로 구현하라.

### 우선순위 P1: 질문 기능

1. 검증된 날짜 컬럼의 `부터~까지` 범위 조회를 추가하라. 시작·종료 날짜를 구조화 계획에 넣고 전체 값 형식 검증과 경계 포함 여부를 명시한다.
2. 고유값이 50개를 넘는 컬럼에도 안전한 정확 일치 조건을 지원할 별도 계약을 설계하라. 현재 그룹 컬럼은 고유값 50개 이하만 연다.
3. 정렬·상위 N·최솟값·최댓값·합계·평균은 숫자 컬럼 의미와 단위가 검증된 자료에만 연다. 문자열 숫자를 자동 추정하지 마라.
4. 여러 자료 결합은 키 의미와 기준일이 검증된 경우만 구현한다. 이름이 비슷하다는 이유로 조인하지 마라.
5. `현재`, `운영 중`, `예약 가능`은 실제 상태 컬럼과 갱신 기준이 확인되기 전까지 계속 거절한다.
6. 결과가 50개 제한에 도달하면 생략 가능성을 표시하고 전체 합계를 표시된 그룹 합계로 오인하지 않도록 한다.

### 우선순위 P1: 운영 안정성

1. 로컬 PostgreSQL 볼륨의 정기 백업, 보관 주기, 복구 리허설을 구현하고 문서화하라. 백업에 비밀이나 원본이 포함되므로 Git에 올리지 마라.
2. 웹·API·n8n·DB 상태 점검과 실패 원인 기록을 추가하라. 사용자의 질문 내용 전체를 불필요하게 로그에 남기지 마라.
3. 컨테이너 재시작 후 OpenAI 키, 읽기 전용 DB 역할, n8n 네트워크 연결이 유지되는지 자동 점검하라.
4. 현재 사이트는 `localhost` 전용이다. 외부 공개가 필요하면 인증, TLS, 접근 제어, 비밀 관리, 네트워크 노출 범위를 먼저 설계하고 사용자 승인을 받아라.

### 우선순위 P2: 수집 갱신

1. 현재 신규 대량 CSV는 기준 스냅샷이며 자동 갱신이 꺼져 있다. 스트리밍 재수집·재검증·변경 이력·이전 정상본 유지 경로를 완성한 뒤에만 스케줄을 켜라.
2. 포털 원본 변경 시 자료별 전체 스냅샷 비교가 메모리와 디스크 한도 안에서 동작하는지 대용량 파일로 시험하라.
3. 외부 링크만 있는 `15136680`, `15136675`는 공식 원본 위치와 이용 조건을 수동 확인한 뒤 처리한다. HTML을 CSV로 간주하지 마라.
4. Supabase Free에는 대량 데이터를 다시 적재하지 마라. 로컬 DB가 현재 운영 경로다.

## 11. 다음 작업의 권장 시작점

가장 먼저 **분석 가능 컬럼 계약 캐시**를 설계·구현하라. 목적은 질문 때마다 대용량 JSONB 전체를 프로파일링하지 않고도 날짜·분류·숫자 컬럼의 의미와 검증 근거를 안전하게 사용할 수 있게 하는 것이다.

권장 순서:

1. 실제 `analytics.dataset_sources`, `analytics.current_dataset_records` 계약과 기존 행사·자동차·공공시설 뷰를 읽기 전용으로 다시 확인한다.
2. 현재 `_columns()`의 실행 시간과 실패 자료를 측정한다. 비밀과 원본 값은 출력하지 않는다.
3. 분석 저장소 소유의 계약 구조를 제안한다. 최소 필드: 데이터셋 ID, 컬럼명, 허용 연산, 의미 유형, 날짜 형식 또는 분류 값 정책, 검증 시각, 원본 SHA/수집 실행 ID, 검증 상태와 실패 이유.
4. 수집 DB의 원본을 수정하지 않고 분석용 마이그레이션 또는 버전 관리된 설정으로 구현한다.
5. 계약이 없거나 원본이 바뀌면 해당 연산을 닫고 명확한 제한 안내를 반환한다.
6. 대표 질문과 대용량 자료의 성능 회귀 테스트를 추가한다.
7. 웹 → n8n → 분석 API 종단 테스트 후 문서를 갱신한다.

## 12. 작업 완료 기준

각 작업은 다음 조건을 모두 만족해야 완료다.

- 사용자 요청이 웹 UI에서 끝까지 동작한다.
- 모델 출력은 구조화 계획으로만 사용되고 서버 검증을 통과한다.
- 읽기 전용 DB 계정과 트랜잭션을 사용한다.
- 결과에 실제 데이터셋과 출처·기준일·수집일·필터·계산 근거가 있다.
- 지원하지 않는 질문을 임의의 전체 건수로 바꾸지 않는다.
- 키·접속 문자열·원본 파일·상태 파일이 로그와 Git에 없다.
- 의미 있는 단위 테스트, 실제 DB 테스트, 필요 시 실제 OpenAI·n8n 테스트가 통과한다.
- 컨테이너를 다시 빌드하고 `http://localhost:8501`에서 사용자 흐름을 확인한다.
- README와 관련 운영 문서를 실제 상태에 맞게 갱신한다.
- 기존 사용자 변경과 Git 이력을 보존하고 일반 커밋·푸시만 사용한다.

작업 시작 시 현재 상태를 5~10줄로 먼저 브리핑한 뒤 바로 구현을 이어가라. 직접 호출하거나 확인하지 않은 기능을 완료로 표시하지 마라.
