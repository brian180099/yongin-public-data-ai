# 공공데이터 질문 분석 서비스 구조

## 운영 흐름

```text
Streamlit 웹
  → n8n YNGN03QuestionAgentV1
    → 요청 ID·입력 크기·문맥 검증
      → 질문 분석 API /v1/analyze
        → LLM 질문 의미·출력 형태 구조화
        → 실제 카탈로그에서 자료 선택
        → LLM 또는 규칙으로 허용 조회 계획 생성
        → 서버가 데이터셋·컬럼·조건·연산 검증
        → 읽기 전용 SQL/Python 계산
        → LLM이 DB 결과에서 설명할 비교 선택
        → 서버가 비교와 숫자를 재검증·계산
      ← 근거·단계 상태·표현 형식을 포함한 JSON
  ← 표·차트·텍스트 렌더링
```

## 역할 경계

| 구성요소 | 담당 | 금지 |
|---|---|---|
| n8n | Webhook, 요청 ID, 입력 제한, API 전달, 오류 응답, 실행 기록 | 별도 답변 생성, SQL, 두 번째 분석 경로 |
| LLM | 질문 목표·출력 형태 해석, 자료·조회 계획 후보, 결과에서 설명할 비교 선택 | SQL 실행, 숫자 계산, 허용 컬럼 결정, 출처 생성 |
| 분석 서버 | LLM 출력 검증, 허용 연산 결정, 문맥 검증, 답변 계약 생성 | 수집 DB 쓰기, 임의 SQL |
| PostgreSQL/Python | 필터·집계·합계·차이·최대·최소 계산 | 자연어 의미 추정 |
| 수집 프로젝트 | 원본·현재 레코드·변경 이력·수집 계약 근거 제공 | 질문 답변, 분석 통계, OpenAI 호출 |

## LLM 사용 단계

1. `question_understanding`: 모든 정상 자연어 질문에서 목표, 요청 출력 형식, 설명 길이를 JSON Schema로 해석한다.
2. `dataset_selection`: 규칙으로 자료를 하나 고르지 못한 경우 실제 DB 카탈로그 안에서만 선택한다.
3. `query_plan`: 조건이나 집계가 있는 질문을 허용된 데이터셋·컬럼·연산 계획으로 변환한다.
4. `result_interpretation`: DB 계산 결과가 여러 항목이면 설명할 최대·최소·차이를 선택한다. 숫자와 문장은 서버가 DB 결과로 다시 계산한다.

키가 없거나 모델 호출이 실패하면 규칙 기반으로 지원 가능한 질문만 처리한다. 각 단계 상태는 `ai_usage`와 `pipeline`에 기록한다.

## 응답 형식

- `request_id`: n8n부터 API 응답까지 유지하는 실행 식별자
- `question_understanding`: 목표, 요청 형식, 설명 길이, 질문 요약
- `ai_usage`: 각 LLM 단계의 `completed`, `failed`, `rejected`, `not_used` 상태
- `pipeline`: 질문 이해, 자료 선택, 계획, 계산, 결과 해석의 담당 주체와 상태
- `presentation`: 사용자가 요청한 형식과 서버가 검증한 실제 표시 형식
- `result`: DB/Python이 계산한 제한된 결과
- `answer`, `insight`: 계산 답변과 검증을 통과한 AI 분석
- `sources`, `filters`, `calculation`, `limitations`: 출처와 재현 근거

## 표현 형식 검증

- 월별·연도별: 선 차트, 막대 차트, 표, 텍스트
- 지역·분류·인구 비교: 막대 차트, 표, 텍스트
- 원본 목록·자료 목록: 표 또는 텍스트
- 단일 건수: 텍스트와 지표

질문과 맞지 않는 형식은 안전한 형식으로 바꾸고 `limitations`에 이유를 남긴다.
