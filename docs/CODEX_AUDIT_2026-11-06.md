## 이번 점검의 실제 확인

- 분석 저장소 `main`은 `origin/main`과 일치했고 점검 시작 시 작업 트리는 깨끗했다. 수집 저장소는 로컬 `main`이 `origin/main`보다 한 커밋 앞서 있었다. 두 저장소의 원본 데이터와 Git 이력은 변경하지 않았다.
- 웹 `/_stcore/health`와 분석 API `/health`가 각각 HTTP 200이었다. n8n Webhook으로 자료 목록을 요청해 `ok`, 316개 데이터셋을 받았다. 관련 컨테이너 6개가 실행 중이었다.
- 분석 저장소의 기본 테스트는 통과했고 라이브 테스트는 기본 설정에서 건너뛰었다. 수집 저장소 기본 테스트는 59개 통과했다.
- 실제 DB·OpenAI·n8n을 모두 켠 전체 테스트의 첫 실행에서는 `test_live_questions`의 숲체험 8,830건 질문이 `unsupported`로 실패했다. 같은 전체 테스트 재실행은 모두 통과했다. 실제 모델을 사용한 같은 질문을 추가로 4회 호출했을 때도 모두 성공했다. 따라서 간헐적 실패가 남아 있다. 실패 원인은 아직 확정하지 않았다.
- 키를 명시적으로 끈 분석 함수(`api_key=''`)에서 숲체험 8,830건, 도서관 문구 검색 1건, 2025년 숲체험 0건을 각각 확인했다. 다른 도시 요청과 임의 SQL은 `unsupported`로 거절됐다. 모델 없이 숲체험 질문을 6회 반복했을 때 모두 성공했다.
- 브라우저 자동화 도구가 로컬 브라우저 호스트에 연결하지 못해, 실제 화면에서 클릭·입력·근거 펼침을 육안으로 확인하지는 못했다. 웹 HTTP 상태와 Webhook 응답 검증을 화면 시각 검증으로 간주하지 않는다.

## 부족한 부분과 우선순위

1. **P0 — 간헐적 제한 시간 실패:** 단순 숲체험 건수 질문에 `_basic_count()`가 `False`여서 `_columns()`가 JSONB 컬럼 전체를 프로파일링한다. 키 없는 반복 호출은 약 2.3초였고 DB 명령 제한은 5초다. 이것이 첫 실패의 원인인지 계측으로 확인한 뒤, 원본 변경 없이 데이터셋별 검증 컬럼 계약을 캐시하고 원본 변경 시 무효화하는 방식이 필요하다.
2. **P0 — 검증·응답 비용:** 자료 목록도 매 요청 DB에서 읽는다. 전체 316개 자료의 동적 발견은 구현되어 있지만, 데이터량이 더 늘면 자료 선택과 컬럼 검증의 지연·실패율을 측정해야 한다. 전체 테스트를 한 번 통과한 결과만으로 안정성을 완료 처리하지 않는다.
3. **P1 — 운영 안정성:** 로컬 DB의 정기 백업, 보관·복구 시험, 재시작 후 DB 읽기 역할·n8n·모델 키 연결 확인이 아직 자동화되지 않았다. 현재 사이트는 `localhost`에서만 열리며 외부 공개 주소는 없다.
4. **P1 — UI 시각 검증:** 코드상 예시 질문, 채팅, 자료 선택, 건수·차트·출처 펼침은 있으나 이번 점검에서는 실제 화면 사용 시험을 완료하지 못했다. 사용자 화면에서 대표 질문·모호한 질문·후속 질문·실패 표시를 확인해야 한다.
5. **P1 — 문서 기준 통일:** 분석 저장소의 `docs/PROJECT_STATUS.md`에는 예전 Supabase/8090 상태가 남아 있고, `docs/CLAUDE_CODE_HANDOFF.md`는 이전 인수인계 문서다. 수집 저장소의 `AGENTS.md` 및 README 일부에도 이전 Supabase/구 분석 서비스 설명이 남아 있다. 현재 운영 기준은 양 저장소 README의 최신 상단 안내와 `docs/BULK_CSV_EXPANSION.md`다. 이후 작업자는 Codex만 사용한다.
