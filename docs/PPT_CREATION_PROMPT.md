# 공공데이터 분석 서비스 PPT 제작 프롬프트

아래 내용을 PPT 제작 AI에 그대로 입력한다. 본문에 없는 숫자나 완료 상태를 임의로 추가하지 않는다.

```markdown
다음 프로젝을 설명하는 16:9 한국어 PowerPoint 발표자료를 만들어줘.

## 발표 목적과 청중

- 청중: AI·데이터 프로젝 평가자, 개발 팀, 공공데이터 서비스 기획자
- 발표 시간: 10~12분
- 목적: 사용자 질문이 실제 공공데이터 근거가 있는 분석 답변과 시각화로 바뀌는 전체 흐름을 쉽게 설명한다.
- 핵심 메시지: LLM은 질문의 의미와 설명을 담당하고, DB·SQL·Python은 사실 조회와 계산을 담당한다.
- 제품명은 `공공데이터 분석 서비스`로 쓴다. `용인시 공공데이터 서비스`를 제품명으로 쓰지 말고, 용인시는 현재 MVP 검증 지역으로 표현한다.

## 작성 원칙

- 전체 13장으로 구성한다.
- 한 슬라이드에는 하나의 주요 메시지만 담는다.
- 제목은 짧고 구체적인 명사구나 검증된 핵심 문장으로 쓴다.
- 과장된 표현, 광고성 문구, 추상적인 AI 수식어를 쓰지 않는다.
- 회사소개서처럼 카드를 반복하는 대시보드형 디자인을 피한다.
- 스톡 사진 대신 실제 웹 화면, n8n 화면, 편집 가능한 플로우 다이어그램, 검증 수치 차트를 사용한다.
- 완료, 현재 제한, 향후 계획을 시각적으로 명확히 나눈다.
- 발표자 노트에는 해당 슬라이드의 설명을 30~50초 분량으로 작성한다.
- 모든 다이어그램·표·차트는 PowerPoint에서 편집 가능한 객체로 만든다.

## 디자인 방향

- 스타일: 신뢰감 있는 공공 기술 서비스, 간결한 데이터 스토리텔링
- 배경: 밝은 아이보리 또는 흰색
- 주조색: 네이비 `#18324A`
- 보조색: 틸 `#168C8C`
- 강조색: 오렌지 `#EF7D32`
- 제한·주의: 붉은색 `#C84B4B`을 작은 부분에만 사용
- 글꼴: Pretendard 또는 Noto Sans KR
- 크기: 표지 42pt 이상, 슬라이드 제목 30~34pt, 본문 18pt 이상
- 각 슬라이드의 텍스트는 최대 5개 핵심 항목 이내로 제한한다.

## 슬라이드 구성

### 1. 표지

- 제목: `공공데이터 분석 서비스`
- 부제: `자연어 질문을 검증 가능한 데이터 답변으로`
- 하단 문구: `현재 MVP 검증 지역: 용인시`
- 디자인: 질문 문장이 데이터 테이블과 차트로 연결되는 절제된 비주얼. 상세 아키텍처는 넣지 않는다.

### 2. 기존 공공데이터 이용의 어려움

- 사용자는 필요한 CSV를 직접 찾고, 컬럼 의미를 파악하고, 계산해야 한다.
- 비슷한 이름의 자료가 많고 자료별 컬럼 구조가 다르다.
- 단순 LLM 답변은 출처·시점·계산 근거를 틀릴 수 있다.
- 시각: `파일 탐색 → 컬럼 해석 → 필터 작성 → 계산 → 설명` 단계를 가로 흐름으로 표현한다. 화살표 문자는 쓰지 말고 연결선을 사용한다.

### 3. 제품 목표와 MVP 범위

- 제품 비전: 질문만 입력하면 적절한 공공데이터를 찾고 근거가 있는 분석을 제공한다.
- 현재 MVP: 경기도 용인시 제공 CSV를 중심으로 검증한다.
- 확장 방향: 동일한 계약·검증 구조를 다른 지자체와 공공기관 데이터에 적용한다.
- 시각: 큰 원으로 `공공데이터 분석 플랫폼`, 안쪽에 현재 검증 영역 `용인시 MVP`를 표시한다.

### 4. 두 프로젝의 역할 분리

- 왼쪽 `수집 프로젝`
  - 공공데이터포털 CSV 수집
  - 스키마·건수·필수값 품질 검증
  - 원본, 현재 레코드, 변경 이력 보존
  - 갱신 실패 시 이전 정상본 유지
- 오른쪽 `질문 분석 프로젝`
  - 질문 의미 해석과 자료 선택
  - 검증된 조회 계획 생성
  - 읽기 전용 DB 계산
  - 한국어 답변, 표, 차트, 출처 표시
- 중앙에 `읽기 전용 analytics 계약`을 두고 두 프로젝의 경계를 표시한다.
- 핵심 문구: `수집기는 사실을 보존하고, 분석기는 질문에 답한다.`

### 5. 사용자 경험 흐름

- 예시 질문: `용인시 청년 인구를 구별 막대 차트로 비교해줘`
- 단계: 채팅 입력, 질문 이해, 자료 선택, 계산, 답변·시각화·근거 확인
- 후속 질문 예시: `그중에서 가장 많은 구는?`, `표로 다시 보여줘`
- 시각: 사용자의 한 문장이 최종 화면의 답변, 차트, 출처로 이어지는 여정 지도로 표현한다.

### 6. 전체 시스템 구조

- 편집 가능한 가로 아키텍처 다이어그램을 사용한다.
- 구성: `Streamlit 웹`, `n8n Webhook`, `질문 분석 API`, `OpenAI`, `읽기 전용 PostgreSQL/Supabase analytics 뷰`, `응답 렌더링`
- 정방향 흐름: 질문, 요청 ID, 조회 계획, DB 결과, 출처·표·차트
- 별도 수집 흐름: `공공데이터포털`, `수집·검증`, `원본/현재/변경 이력`
- 수집 흐름과 질문 흐름이 직접 섞이지 않고 analytics 읽기 계약으로만 연결되는 구조를 강조한다.

### 7. LLM과 DB의 역할

- 좌측 `LLM`
  - 질문 목표·의미·출력 형식 해석
  - 복잡한 질문의 자료·조회 계획 후보 생성
  - DB 결과에서 설명할 비교 항목 선택
- 우측 `DB·SQL·Python`
  - 원본 검색, 필터, 집계, 합계, 차이 계산
  - 결과 건수와 표·차트 데이터 생성
  - 계산 제한과 실행 시간 제어
- 중앙 `분석 서버 검증`
  - 데이터셋 ID·컬럼·연산·조건 허용 목록 대조
  - LLM이 만든 SQL을 실행하지 않음
  - 모델이 선택한 비교를 DB 결과와 재대조
- 핵심 문구: `자연어는 LLM, 숫자와 근거는 DB`

### 8. n8n의 역할과 실제 워크플로

- 현재 5개 노드를 가로 플로우로 표시한다.
  1. 외부 질문 받기
  2. 질문 입력 검증
  3. 허용된 분석 조회 실행
  4. 응답 계약 정리
  5. 근거 포함 JSON 응답
- n8n은 요청 ID, 입력 제한, API 전달, 오류 응답, 실행 기록을 담당한다.
- n8n 안에서 별도 LLM 답변이나 SQL을 생성하지 않는다.
- 가능하면 제공된 실제 n8n 스크린샷을 사용하고, 이름과 노드 흐름이 읽히도록 크롭한다.

### 9. 데이터 신뢰성과 안전 장치

- 데이터셋 목록과 건수를 DB에서 동적으로 읽고 코드에 고정하지 않는다.
- 검증된 날짜·지역·분류·숫자 컬럼에만 해당 연산을 허용한다.
- 읽기 전용 계정과 트랜잭션, 5초 DB 제한, 최대 20건 원본 표시 제한을 사용한다.
- 답변에 데이터셋명, 제공기관, 공식 URL, 데이터 기준일, 수집일, 필터, 계산 방법을 표시한다.
- `등록 현황`을 `현재 운영 중`, `예약 가능`, `현재 행사`로 단정하지 않는다.
- 시각: 원본 보존, 컬럼 계약, 읽기 전용 계산, 근거 표시를 계층형 방어 구조로 표현한다.

### 10. 실제 질문과 검증 결과

- 표 열: `사용자 질문`, `적용 연산`, `검증 결과`, `표시 형식`
- 행 1: `숲체험일정은 몇 건이야?` / 전체 건수 / `8,830건` / 텍스트·출처
- 행 2: `도서관 달력에서 '유아 클레이 특강'은 몇 건이야?` / 원본 문구 검색 / `1건` / 텍스트·근거
- 행 3: `2025년 숲체험일정은 몇 건이야?` / 검증된 날짜 컬럼 필터 / `0건` / 텍스트·필터
- 행 4: `용인시 청년 인구를 구별 비교해줘` / 검증된 숫자 컬럼 합계 / `청년 208,775명` / 막대 차트·표
- 주의 문구: `39행은 행정동 기록 수이며 인구 수가 아니다.`
- 숫자는 텍스트로만 나열하지 말고, 질문과 검증 방식을 한눈에 비교하는 표로 만든다.

### 11. 사용자에게 보이는 결과

- 실제 웹 화면 스크린샷을 큰 비율로 배치한다.
- 화면에서 다음 영역을 번호로 연결해 설명한다.
  1. 자연어 질문
  2. DB 계산 답변
  3. 표 또는 차트
  4. AI 분석 문장
  5. 출처 및 조회 기준
- 사용자가 `표로`, `막대 차트로`, `선 차트로`, `간단히`, `자세히`를 질문에 직접 적을 수 있음을 보여 준다.
- 거대한 UI 모의 화면을 새로 그리지 말고 실제 스크린샷을 사용한다.

### 12. 현재 검증 상태와 남은 제한

- `검증 완료`
  - 기본·라이브 포함 전체 자동 테스트 57개 통과
  - 실제 로컬 PostgreSQL, OpenAI 구조화 출력, n8n Webhook 종단 흐름 확인
  - 웹 HTTP 200, API 정상, 구 Webhook 404, 구 분석 컨테이너 중지
- `현재 제한`
  - 임의 날짜 범위, 평균, 순위, 상위 N, 다중 자료 결합은 미지원
  - n8n 공개 운영 전 Webhook 인증·호출 제한·실행 데이터 보존 최소화 필요
  - 최근 실측에서 `숲체험일정`이 불관련 후보로 선정되는 회귀가 발견됨. n8n 문제가 아니라 분석 서버의 자료 선정 안정성 문제로 분리함.
- 완료와 제한을 같은 색으로 표시하지 말고 좌우 대조 구조로 명확히 구분한다.

### 13. 확장 로드맵과 마무리

- 1단계 `안정화`
  - 자료 후보 선정 회귀 수정
  - n8n Webhook·내부 API 인증과 호출 제한
  - DB 백업·복구와 장애 알림
- 2단계 `분석 확장`
  - 검증된 숫자 컬럼의 합계·평균·상위 N
  - 임의 날짜 범위와 비교 기준
  - 자료별 컬럼 계약 확대
- 3단계 `지역·기관 확장`
  - 용인시 MVP에서 검증한 수집·분석 계약을 다른 공공데이터에 재사용
- 마무리 문장: `자연어 질문을 출처와 계산 근거가 남는 공공데이터 분석으로 전환한다.`
- 마지막 슬라이드에 새로운 기능이 이미 완성된 것처럼 표현하지 않는다.

## 수치와 상태 표현 주의

- `8,830건`, `1건`, `2025년 0건`, `청년 208,775명`, `57개 테스트 통과`는 실제 검증 결과로 사용할 수 있다.
- `39행`을 인구 39명으로 표현하지 않는다.
- 등록된 행사·시설·일정을 현재 운영 중이나 예약 가능으로 단정하지 않는다.
- 자동 테스트 57개 통과와 최근 발견된 자료 선정 회귀를 함께 표시해, 검증 이력과 현재 운영 위험을 혼동하지 않는다.
- 로컬 316개·Supabase 246개 카탈로그 수치는 2026-11-06 점검 시점의 스냅샷이므로, 사용하려면 `해당 시점 점검값`이라고 표시한다. 핵심 슬라이드에서는 생략해도 된다.
```
